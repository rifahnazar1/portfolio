Inbox Copilot

An AI-powered customer-support workflow that drafts replies, checks its own confidence, and routes uncertain cases to a human before anything reaches the customer.

Overview

Inbox Copilot turns an inbound support inbox into a semi-autonomous workflow. Incoming Gmail messages are classified, matched against an FAQ knowledge base, and answered by Claude. Every draft is scored for confidence — high-confidence replies are queued for one-click human approval in Slack, while low-confidence or sensitive cases are escalated. Approved replies are sent back through Gmail, and every step is logged to Google Sheets for auditing.

Engineering decisions

Why human approval?

Support replies are customer-facing and hard to unsend. A human approval gate makes the worst-case outcome "a reply is delayed" instead of "a wrong or off-brand reply was sent." It also produced a stream of labelled good/bad drafts I could use to evaluate and improve the system.

Why confidence thresholds?

Not every message deserves the same trust. Claude returns a confidence score alongside each draft; above the threshold the draft is queued for quick approval, below it the message is escalated with the reason. This concentrates human attention on exactly the cases where the model is unsure.

Why JSON output?

The model returns a strict JSON object — intent, chosen FAQ, draft reply, confidence, and an escalation flag — so downstream n8n nodes can branch on fields instead of parsing prose. Structured output is what makes the confidence gate and logging possible at all.

Failure handling & retry logic

API calls (Gmail, Claude, Slack) are wrapped with bounded retries and exponential backoff. Malformed model output is caught and re-requested once; if it still fails validation, the message is escalated to a human rather than dropped. Nothing silently disappears — every terminal state is logged.

Evaluation

Prompting alone was never going to be trustworthy, so the system was tested against a fixed set of representative scenarios — including the ones designed to make it fail.

Tested six customer scenarios including refund requests, abusive messages, missing FAQs and low-confidence responses — checking not just whether the reply was good, but whether the system correctly escalated when it should have.

Lessons learned

Prompt engineering wasn't enough. Reliability came from evaluation, confidence thresholds and human approval — not from better prompts alone. The prompt gets you a plausible draft; the system around it is what makes the output trustworthy.

The second lesson was that "escalate when unsure" is a feature, not a failure. Once escalation was a first-class outcome, the whole system got easier to reason about and safer to deploy.
