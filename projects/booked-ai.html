Engineering case study Multi-agent

Booked AI

A production multi-agent travel assistant spanning Outlook and WhatsApp, orchestrating 30+ APIs. This is an engineering case study — no confidential code, just the decisions.

This is a written case study rather than a code repository. The product is proprietary, so what follows is the engineering — the problems, the tradeoffs, and my specific contributions — with confidential details omitted.

Problem

Travellers wanted to plan and manage trips by simply messaging — the same way they'd text a knowledgeable travel agent — across the channels they already use: Outlook for email and WhatsApp for chat. Behind that simple interface sits a large amount of real-world complexity: flights, hotels, itineraries, calendars, and payments, each with its own API and failure modes.

Engineering challenges

30+ APIs

Each provider had different auth, schemas, rate limits and error semantics. The system needed a consistent tool interface over inconsistent backends so agents could reason about capabilities rather than HTTP quirks.

State management

A trip is a long-running, multi-turn conversation that can span days and channels. Keeping durable, coherent state — what's booked, what's pending, what the user last asked — across Outlook and WhatsApp was the hardest part.

Latency

Chaining model calls and slow third-party APIs makes latency compound quickly. Keeping responses conversational meant parallelising tool calls, streaming, and being deliberate about when to think versus when to act.

Prompt consistency

With many agents and tools, small prompt drift produced large behavioural drift. Prompts had to be structured, versioned and constrained so behaviour stayed stable across releases.

Evaluation & observability

You cannot improve what you cannot see. Every run was traced so failures could be reproduced, and behaviour was measured against evaluation sets rather than eyeballed.

My contributions

  • I designed the multi-agent graph — how work is decomposed, routed between agents, and recombined into a single reply to the user.
  • I implemented the tool layer that wraps the external APIs behind a consistent, model-friendly interface (via MCP), including retries and error normalisation.
  • I owned the state-management approach that keeps a trip coherent across turns and across the Outlook and WhatsApp channels.
  • I built out the observability and evaluation loop with Langfuse so regressions were caught in tracing and eval, not in production.
